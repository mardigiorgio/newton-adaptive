Which stepping branch runs:
- `ManagerBasedRLEnv.step` has two physics branches keyed on `self._physics_handles_decimation` (I/source/isaaclab/isaaclab/envs/manager_based_rl_env.py:216 vs :228). That flag comes from `self.sim.physics_manager.handles_decimation()` (I/source/isaaclab/isaaclab/envs/manager_based_env.py:208-209), which is `NewtonManager._is_all_graphable()` (I/source/isaaclab_newton/isaaclab_newton/physics/newton_manager.py:3209-3216). `_is_all_graphable` requires an articulation on the `use_newton_actuators=True` fast path (newton_manager.py:3104-3106); that flag defaults to False (I/source/isaaclab/isaaclab/sim/simulation_cfg.py:87) and the spatula task never sets it (no hits in the task dir), and its actuators are all `ImplicitActuatorCfg` on the standard Lab path (I/.../trossen_spatula_lift/assets.py:78-105). So `handles_decimation()` is False and env.step takes the **python decimation loop**: `for _ in range(self.cfg.decimation): apply_action; write_data_to_sim; self.sim.step(render=False); scene.update(dt=self.physics_dt)` — manager_based_rl_env.py:228-243. (`NewtonManager._decimation` is still set to 2 by `set_decimation` at newton_manager.py:3204 via manager_based_env.py:208, but `_decimation` is only consumed by `_simulate_full` (newton_manager.py:2394), which does not run on this path.)

What one `sim.step(render=False)` does (NewtonManager.step, newton_manager.py:948-1038):
- solver-internal-reset delegate on the pending world mask (newton_manager.py:977), model-change notify (:980-984), `cls.forward()` (:1004, which re-runs the reset delegate and FK on the masks then zeroes them, newton_manager.py:636-641), then — since the adaptive backend reports no manager-level CUDA-graph support (`_supports_cuda_graph_capture` returns False unless `NEWTON_MJ_ADAPTIVE_CONDITIONAL=1`, I/source/isaaclab_newton/isaaclab_newton/physics/mjwarp_manager.py:544-560) — the non-graph, non-all-graphable branch runs `cls._simulate_physics_only()` (newton_manager.py:1017-1029).
- `_simulate_physics_only`: because `use_mujoco_contacts=False` sets `_needs_collision_pipeline=True` (mjwarp_manager.py:391), it runs `cls._collision_pipeline.collide(cls._state_0, cls._contacts)` then `cls._run_solver_substeps(contacts)` then post-step callbacks + `_update_sensors` (newton_manager.py:2410-2425).
- `_run_solver_substeps` is overridden for adaptive: with `NEWTON_ADAPTIVE_SINGLE_BOUNDARY` unset/`"1"` it makes **exactly one boundary call**: `cls._step_solver(cls._state_0, cls._state_0, cls._control, contacts, cls._solver_dt * cls._num_substeps)` (mjwarp_manager.py:459-462), which lands on `cls._solver.step(state_0, state_1, control, contacts, substep_dt)` (mjwarp_manager.py:444).

The dt value:
- `NewtonManager._solver_dt = cls.get_physics_dt() / cls._num_substeps` with `_num_substeps = cfg.num_substeps` (newton_manager.py:2064-2066); `get_physics_dt()` returns `sim.cfg.dt` (I/source/isaaclab/isaaclab/physics/physics_manager.py:469-471). With sim.dt=0.01 and num_substeps=1: `_solver_dt = 0.01`, and the boundary call receives `_solver_dt * _num_substeps = 0.01`. **Each boundary call gets dt_outer = 0.01 s, not 0.02.** (Even with `NEWTON_ADAPTIVE_SINGLE_BOUNDARY=0`, the fallback per-substep loop at newton_manager.py:2347-2356 issues num_substeps=1 call of `_solver_dt=0.01` — identical for this task.)
- On the solver side this `step(...)` IS the boundary call; `step_dt` is a thin alias calling `self.step(state_0, state_1, control, None, dt_outer, ...)` (N/newton/_src/solvers/mujoco/solver_mujoco_adaptive.py:2124-2137), and `step` requires dt and marches every world exactly `dt_outer` (solver_mujoco_adaptive.py:1783-1811, `effective_dt_max = min(self._dt_max, dt_outer)` at :1813).

Count per iteration:
- 1 env.step = decimation (2) x sim.step = **2 boundary calls of dt_outer=0.01** (manager_based_rl_env.py:228-235 + mjwarp_manager.py:459-460).
- 1 training iteration = num_steps_per_env (24) x 2 = **48 boundary calls** (on_policy_runner.py:83 x manager_based_rl_env.py:228). This matches tonight's telemetry of ~48 boundaries/iteration (`_log_march_boundary` fires once per boundary when `_march_log_path` is set, solver_mujoco_adaptive.py:1929-1930).

## 3. Env-side work between two boundary calls

Between the two sim.step calls inside one env.step (same decimation loop, manager_based_rl_env.py:228-243):

- `self.scene.update(dt=self.physics_dt)` (:243) — asset data refresh; articulation data reads are views bound directly to Newton `state_0`/`control` arrays (`_sim_bind_joint_pos = self._root_view.get_dof_positions(SimulationManager.get_state_0())...`, I/source/isaaclab_newton/isaaclab_newton/assets/articulation/articulation_data.py:1680-1692) — no per-step host copy at this layer.

Between two env.steps (control boundary), after the decimation loop (manager_based_rl_env.py:245-307):
- counters (:247-248), `termination_manager.compute()` (:250), `reward_manager.compute(dt=self.step_dt)` (:254), then resets, then `command_manager.compute` (:295), interval events (:297-298), and `observation_manager.compute(update_history=True)` (:304) — observations are computed AFTER resets.

Reset path and solver.reset semantics:
- `_reset_idx(reset_env_ids)` (manager_based_rl_env.py:262-270) runs curriculum, `scene.reset`, event-manager `mode="reset"` terms, then per-manager resets (manager_based_rl_env.py:405-444). Event reset terms that write joint/root state go through asset write methods that call `NewtonManager.invalidate_fk(...)`, which ORs env ids into `_world_reset_mask`/`_fk_reset_mask` (newton_manager.py:1414-1458); the masks are consumed at the next forward/step boundary (docstring intent at :1420-1424; consumption at :636-641 and :977).
- Consumption: `NewtonManager.step` calls `cls._reset_solver_internals_delegate(cls._world_reset_mask)` (newton_manager.py:977) and again inside `forward()` (newton_manager.py:636), which zeroes the mask after use (:640-641). The mjwarp specialization for the adaptive backend is unconditional on mask content (only `world_mask is None` short-circuits): `cls._solver.reset(cls._state_0, world_mask=world_mask, flags=0)` (mjwarp_manager.py:526-536) — i.e. an all-False-mask reset launch happens at every step/forward boundary, and only worlds flagged True are actually touched by the kernel.
- What that reset does in the solver: `SolverMuJoCoAdaptive.reset` calls `super().reset(...)` (clears MuJoCo warm-start buffers; `flags=0` preserves the env-authored joint state) and additionally launches `_reset_worlds` restoring per-world controller state — `ideal_dt/dt/dt_half/sim_time/next_time`, the `accepted` and `diverged` latches, and `dt_ceiling` — for masked worlds (N/newton/_src/solvers/mujoco/solver_mujoco_adaptive.py:2143-2186). The `diverged` latch is documented as cleared per world by reset (solver_mujoco_adaptive.py:2192-2199). Note the separate `solver.reset(state_0, world_mask=cls._solver.diverged, flags=0)` after each step at mjwarp_manager.py:419 is the **SAP-adaptive** branch only, not this task's MuJoCo-adaptive path.

## 4. Actions -> mjw ctrl, and env-side reads of solver state

Actuator path (action to ctrl):
- Task actions: `mdp.JointPositionActionCfg` (scale 0.5, clip ±6) for the six arm joints and `BinaryJointPositionActionCfg` for the two gripper carriages (trossen_spatula_lift_env_cfg.py:271-285); all actuator models are `ImplicitActuatorCfg` (assets.py:78-105).
- `action_manager.apply_action()` writes joint position targets into articulation buffers; `scene.write_data_to_sim()` -> `articulation.write_data_to_sim` standard path copies `_joint_pos_target`/`_joint_vel_target`/effort into `_sim_bind_joint_position_target` etc. (articulation.py:427 onward, standard-path branch after :529). Those sim-bind buffers ARE Newton `Control` attributes: `joint_f`, `joint_act`, `joint_target_q`, `joint_target_qd` obtained via `self._root_view.get_attribute(..., SimulationManager.get_control())` (articulation_data.py:1683-1692).
- Inside the boundary call, the solver ingests that control once per boundary: `self._apply_mjc_control(self.model, state_0, control, self.mjw_data)` (solver_mujoco_adaptive.py:1827), which writes `mj_data.ctrl` / `qfrc_applied` (base implementation N/newton/_src/solvers/mujoco/solver_mujoco.py:4713-4721). State conversion Newton->MuJoCo also happens once per boundary (`_update_mjc_data`, solver_mujoco_adaptive.py:1840), injected Newton contacts are converted once per boundary (`_convert_contacts_to_mjwarp`, :1846-1855, required because `use_newton_contacts` from `use_mujoco_contacts=False`), and MuJoCo->Newton conversion back once at the end (`_update_newton_state` + `_copy_state`, :1932-1936). So within one boundary call, control is frozen — consistent with the manager's rationale for one boundary call per decimation tick (mjwarp_manager.py:448-453).

Env-side reads of solver state:
- The task's own mdp.py has no direct solver/NewtonManager reads (grep for solver/NewtonManager/physics_manager in trossen_spatula_lift/mdp.py: no hits); observations/rewards go through articulation/rigid-object data views over `state_0` (articulation_data.py:1680-1692).
- The one direct solver-state read on the hot path is manager telemetry: `NewtonManager.step` ends with `cls._log_solver_debug()` (newton_manager.py:1038); for adaptive that runs `_log_adaptive_telemetry`, which every `NEWTON_ADAPTIVE_LOG_EVERY` (default 30) frames does `cls._solver.dt.numpy()` and `cls._solver.cumulative_substeps()` — host syncs — and appends to `NEWTON_ADAPTIVE_LOG` (default /tmp/newton_adaptive.log) (mjwarp_manager.py:563-585, gating at :587-589).
- The fixed-vs-graph housekeeping reads: the non-adaptive/SAP reset gates do host `local_mask.numpy().any()` (mjwarp_manager.py:530-538), but the adaptive branch returns before those, so no mask sync on this task's path.
